# Yoshling audit 6 October 2026

The dashboard has a useful shared architecture and substantial regression coverage, but current code still admits data loss, world access violations, unsafe memory settings, and several cases of reporting the wrong result. Security and destructive operations should be repaired before adding features.

This is an audit snapshot of commit `6a4d2880640aa5944727c245e8ef93eaab58024c`. It is not a closure record. `CLAUDE.md` tracks current open work; `CLOSED.md` tracks completed work. Findings marked **existing** or **incomplete earlier fix** were compared with the September audit and its refutations. The rest are current findings absent from those records.

Subsequent local remediation is recorded in `CLOSED.md`; source and deployment status is in
`CLAUDE.md`. The diagnoses and original verification below remain the snapshot of that commit.

## Security and deployment

### F01 P1 Uploaded symlinks escape the game file boundary

`src/app/api/7dtd/world/route.ts:441` extracts ZIP symlinks and its placement preserves them. `src/lib/file-guard.ts:72` checks the spelling of a path, while `src/app/api/7dtd/files/route.ts:72` and its read/write branches follow filesystem links.

An isolated existing BusyBox 1.37.0 container, with no network or host mounts, accepted a valid world containing a link named like an ordinary text file. The route's unzip, move, ownership and mode sequence preserved it. Reading the apparently contained path returned fabricated `.env` content outside the game tree. Listing names passed the current ZIP path guard and extraction emitted no warning.

A 7DTD moderator can therefore cross from their granted game into `/opt/yoshling/.env` and host-mounted project files. Reject links in uploaded trees and enforce physical containment for reads and writes, including parent directories of new files. Lexical containment remains useful but cannot establish this boundary by itself.

### F02 P1 The web image contains production credentials

`Dockerfile:11` copies the complete build context, no `.dockerignore` exists, and `Dockerfile:33` copies the standalone output into the runner. This build emitted `.next/standalone/.env` and `dev.db`; the standalone directory was 492 MB. A read-only check inside the production web container confirmed `/app/.env` exists and is 903 bytes. No credential values were printed.

The image and build cache retain credentials beyond the intended runtime environment and bind mount. This establishes credential inclusion, not public disclosure of the image. Exclude secrets, databases, Git metadata and worktrees from the build context; constrain file tracing; verify the resulting image contains none of them. Assess who could obtain existing image/cache copies before deciding which credentials need rotation.

### F03 P1 Runtime dependencies include published critical vulnerabilities

The installed Next.js 16.2.6 falls within the maintainer's affected range for unauthenticated AVIF image optimization remote code execution. The app enables remote image optimization, and its web process runs as root with the Docker socket and host project mounted, which increases the consequence of a web process compromise. Exploitability was not tested. The maintainer identifies 16.3.3 as the fix for this particular advisory. [Next.js advisory](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4)

NextAuth beta.31 and its Auth.js dependency also have advisories. The configuration-error advisory describes checks based merely on an auth object's existence; this project's `session?.user` checks need applicability review, rather than assuming that advisory bypasses them. The email-normalization advisory does not describe the Discord-only configuration. [Auth.js configuration advisory](https://github.com/nextauthjs/next-auth/security/advisories/GHSA-8fpg-xm3f-6cx3)

Prioritize supported patched runtime packages, then evaluate transitive and development findings. `npm audit fix --force` is unsuitable as an automatic remedy: its proposed resolutions include major changes and downgrades. The 38 entries are not 38 demonstrated application exploits.

### F04 P1 Upload POST omits world authorization

`src/app/api/7dtd/world/route.ts:231` checks `world.upload` capability but never checks the session's 7DTD grant. A MOD granted only PZ can directly upload a small 7DTD world/save using their normal session, including replacing a non-current save. GET, DELETE and token mint enforce the world gate; POST's session branch does not.

Add the same world gate before reading a body or admitting an operation. This is a backend authorization defect, distinct from the UI showing forbidden controls. Evidence is the complete POST authorization branch and the permission table.

### F05 P2 Display names cannot identify invited Discord accounts

`src/lib/auth.ts:20` passes both the username and `global_name` to `isWhitelisted`; `src/lib/whitelist.ts:113` accepts a match on either. A different Discord ID presenting an allowed display name passes the sign-in gate. Discord describes `global_name` as a display name and provides a separate account ID. [Discord user structure](https://docs.discord.com/developers/resources/user#user-object)

Existing production accounts prevent this from immediately creating another ADMIN: a new account starts as MEMBER with no worlds. On a fresh database the first admitted account becomes ADMIN, increasing the bootstrap consequence. Resolve invitations to Discord IDs and keep names as labels. This finding concerns identity matching, separate from the deliberately documented empty-list behavior.

### F06 P1 PZ image deployment bypasses graceful stop and world admission

**Existing and explicitly documented, still present.** `scripts/deploy.sh:186` uses `docker compose up -d --no-deps "$SERVICE"` for both web and PZ. For `--service zomboid`, it starts a stopped world alongside another running game, or recreates a running PZ through the signal path the game ignores, eventually forcing its termination.

The current `CLAUDE.md` workaround is necessary. The script needs the same graceful stop, stopped-state preservation and world admission as application control. No deployment was performed during this audit.

## World control and data safety

### F07 P1 Reset can discard its own safety copy

`src/app/api/7dtd/reset/route.ts:169` names snapshots with the world before the timestamp; `:190` sorts complete names descending and retains only two. An isolated reproduction with two older `Zulu` snapshots and a new `Alpha` snapshot retained the older Zulu files and deleted the new Alpha file. The route then wipes Alpha at `:237` and still says it backed up the old save.

Order by actual creation time, explicitly protect the current snapshot, and verify its survival before wiping. A different world name is enough to trigger this; a failed tar is not required.

### F08 P1 Reset can start a second world

`src/app/api/7dtd/reset/route.ts:231` captures whether 7DTD was running for the stop, then `:257` starts it unconditionally. `startGameForOperation` reaches the raw driver start without co-residency refusal or eviction.

With PZ running and 7DTD stopped, Reset can leave both running. Holding the operation's power resource serializes actions but does not enforce the single-world invariant. Validate/admit the intended final state before any destructive work; deliberately preserve stopped state or perform the normal confirmed handoff.

### F09 P1 Minecraft can allocate a heap larger than its container

`src/lib/game-manager.ts:2060` validates against host RAM, giving approximately 13 GB on this box; the Minecraft `mem_limit: 6g` in `docker-compose.yml` fixes its container at 6 GB. The apply changes `MEMORY` and recreates that same 6 GB container.

An isolated execution of the actual `setMemory` logic accepted 7 GB, requested `MEMORY=7G`, and could return `applied:true` from the environment comparison. Matching env values cannot make a heap larger than the container safe. Derive each game's ceiling from its actual container limit with non-heap headroom, or update and verify the limit together with the heap. No unsafe heap was applied live.

### F10 P1 A refused settings change makes the retry falsely succeed

**Incomplete earlier fix.** `src/app/api/settings/route.ts:123` updates the DB before `applyServiceEnv` acquires admission at `:149`. A busy or failed apply leaves the desired version in the DB. The next request compares with that row at `:77`, decides there is no change, and returns success without recreating anything.

Actual-route isolated execution: first version change returned 409 but changed the DB; retry returned 200 with zero container applies. Compare against actual configured/container state and place the persisted change inside the admitted operation, with a retryable failure state. The documented closure of honest apply failure does not cover this mechanism.

### F11 P1 Dollar signs corrupt XML settings

`src/app/api/7dtd/config/route.ts:254` and `config/all/route.ts:235` interpolate escaped XML values into JavaScript replacement strings. XML escaping does not neutralize replacement tokens. Exact-code execution changed requested `pa$$word` into `pa$word`; `$&` inserted the matched XML into the attribute and malformed the document.

Names, descriptions, passwords and `reset/route.ts:39` share this problem. Use replacement callbacks or a writer that treats the value literally, then parse/read back the stored value. The curated config DB and response currently retain the requested value, so they can hide the corruption.

### F12 P1 Settings can overwrite real data after an initial read fails

`src/app/minecraft/settings/page.tsx:111` initializes ops/whitelist as empty arrays, swallows initial failures, and leaves Save available. A transient failed GET followed by Save empties the corresponding live list; adding one entry instead replaces every existing entry with that one.

`src/app/7dtd/settings/page.tsx:55` similarly leaves the quick form populated with fallback name, blank password, eight players and blank sandbox code; Save submits those defaults after a failed read. Require a successful load of each independent resource before its write controls become active and offer retry. This is the already-fixed app whitelist failure class in other current forms.

### F13 P1 Restoring 7DTD also restores an obsolete control password

`src/app/api/7dtd/backups/route.ts:341` writes archived `sdtdserver.xml` verbatim. The game's telnet password lives in that XML, while the web container continues using the current env password. The image's env value does not repair the XML on ordinary startup.

A read-only comparison of the newest production 7DTD archive, `7dtd-Reveo_Valley-2026-10-05T14-07-41.tar.gz`, confirmed its telnet password differs from the current XML; the current XML matches the running web env. Thus a current available restore point would revert this credential. Preserve deployment-owned control settings during restore and verify that control still authenticates. No restore or password value disclosure occurred.

### F14 P1 Pack apply modifies a potentially running world without power protection

**Existing open work.** `src/app/api/mods/install-modpack/route.ts` holds the Minecraft file resource but does not stop the game, claim power, or check pre-emption at its destructive steps. Jars can be replaced beneath a running JVM and a concurrent power action can begin during the replacement.

Use the documented `withGameStopped` pattern with `restartOnFailure:false`, the power resource, and step-boundary pre-emption guards. Preserve the rollback point before replacement. This audit does not re-report the closed compose-clobber bug.

### F15 P2 Short writes check resources without reserving them

**Existing concurrency problem, affecting the newer sandbox writer too.** `src/lib/operation-response.ts:40` calls `assertResourceFree`; neither function reserves a resource. A request can pass, await body/file/network I/O, then overlap another short writer or a newly admitted restore.

PZ mods reads the list before waiting for Steam at `mods/route.ts:267`; sandbox saves read a whole file at `zomboid-sandbox.ts:133` and rename independent rewrites at `:143`. Two disjoint edits can both read back successfully yet the second later erase the first. Unique temp files prevent temp-name collisions, not lost updates. Reserve/serialize the complete read-modify-write interval, with conflict detection where operators edit stale snapshots.

### F16 P2 ZIP extraction has no expanded size budget

`src/app/api/7dtd/world/route.ts:408` says it rejects ZIP bombs early, but the checks inspect paths and a game-shape marker. The compressed upload budget does not bound uncompressed bytes, file count, or free disk. Extraction at `:441` can fill the host before its time limit expires.

Check declared totals and actual extraction consumption against an explicit expanded budget and available space. The false comment should be corrected with the implementation. This is source-established; no disk exhaustion was attempted.

## Minecraft content and rollback

### F17 P1 Single mod installation ignores required dependencies

`src/app/api/mods/install/route.ts:122` installs the selected mod without processing `selectedVersion.dependencies`. The Install button calls it directly; dependency handling in `mod-card.tsx:155` belongs to Add to Pack.

Actual-route isolated execution using the [public Waystones Fabric 26.1.2 build](https://api.modrinth.com/v2/version/YgvCsKWn), which declared three required projects, installed only Waystones and returned “Mod installed. Restart server to activate.” An empty server can then fail to boot. Resolve the required dependency closure for the chosen build, verify what is installed, and name refusals or omissions before recommending a restart.

### F18 P1 Import silently saves an incomplete pack

`src/app/api/modpacks/import/route.ts:78` turns each failed project lookup into `null`; `:84` filters it out, saves the shorter list, and returns 200 without naming omissions. Apply then measures completeness against that shortened list.

Actual-route isolated execution with two required dependencies and one injected transient lookup failure returned 200 and stored one mod. A later apply can report 100% of a pack whose required content was discarded. Refuse incomplete imports or expose an explicit partial import with the missing identities; never shrink the claimed pack silently.

### F19 P2 Export uses the server target instead of the saved target

`src/app/api/modpacks/[id]/export/route.ts:33` selects Minecraft version and loader from `ServerConfig`, ignoring the saved pack's targets, and labels the export with those server values at `:96`.

Actual-route isolated execution of a saved 1.21.1 set on a 26.1.2 server queried 26.1.2 builds, returned null download links, and described the set as 26.1.2. This contradicts Export's launcher use. Resolve from saved targets/pins and explicitly report entries that cannot be exported.

### F20 P2 A supported version can be rejected by its list position

`src/lib/modpack-resolve.ts:65` can choose a build supporting the server version, but `packNeeds` at `:119` reduces the supported list to its first item. Compatibility and import persist/compare only that first value.

Actual helper execution of a valid build declaring `["26.1", "26.1.2"]` against 26.1.2 first reported a matched build, then an incompatible pack. Preserve the version/loader selected for this server or compare membership in the supported sets. This fixture demonstrates the contract defect; it is not a claim about a particular live pack.

### F21 P2 Minecraft rollback does not fully restore mod metadata

`install-modpack/route.ts:495` omits the inventory when it is empty and strips `source` and `versionId` when it is populated. `server/backups/route.ts:261` restores the inventory only when its length is positive. Rolling back to an empty mods directory leaves the new DB rows; populated rollbacks lose provenance/version pins.

There is also a portability limit: the inventory exists only in the sidecar; MC tar members are world/mods directories, and `archiveResponse` downloads only the tar. Moving that download to a replacement host loses the inventory even though the jars survive. Preserve an explicit empty inventory, retain all required metadata, restore it transactionally, and make the downloadable artifact carry its own inventory. A missing inventory should produce a precise limited result, not a complete rollback claim.

### F22 P2 Pack switches leave untracked jars installed

**Existing mechanism; inventory visibility was fixed.** `install-modpack/route.ts:436` and `:559` remove only DB-tracked mods. A manually copied or otherwise untracked jar remains beside the new set. The newer reconciliation page makes it visible but does not make a pack apply replace it.

Decide and disclose the treatment of every jar before application, then verify the resulting directory against the intended set. Do not imply complete replacement when untracked jars remain. The current Change Pack copy is more honest than the generic saved-set warning.

## Frontend and operation feedback

### F23 P2 HTTP proxy timeouts are presented as operation failures

`src/lib/modpack-apply.ts:131`, `game-backups.tsx:185`, `game-controls.tsx:166`, `game-overview.tsx:186` and `mission-control.tsx:263` treat a resolved HTTP 524 as a normal failure. Swallowing the HTML JSON parse failure produces an empty object; their “still running” catch only handles a rejected fetch.

Actual-code isolated probes with an HTML 524 response returned “Failed to install modpack”, “Backup failed”, “Restore failed”, or “Command failed”. A transport rejection correctly produced the uncertain/still-running result. Long operations continue on the server across this proxy timeout, so these messages can prompt incorrect retries. Reconcile ambiguous gateway responses with the operation ledger and retain the operation identity.

### F24 P2 Saving an unchanged PZ mod editor enables disabled variants

`src/components/zomboid-mods.tsx:247` seeds drafts from `provides` rather than `enabled`. The API intentionally distinguishes all IDs supplied by the Workshop item from the enabled subset; its PATCH replaces that item's enabled IDs with the submitted list at `mods/route.ts:428`.

Edit then Save can enable alternative or B41/B42 IDs without a visible edit. `zomboid.ts:303` documents an actual root/B42 ID distinction. Seed from enabled IDs and reset drafts on cancellation or fresh reads. This is corroborated frontend/backend data flow, not a live configuration change.

### F25 P2 Demoting an ADMIN displays and can grant the wrong worlds

`src/app/users/page.tsx:31` replaces stored grants with ADMIN's effective all-world access. `crew-list.tsx:51` changes only the displayed role on demotion, while the role API preserves stored grants.

A PZ-only moderator promoted to ADMIN, reloaded and then demoted appears to retain all worlds. Toggling the apparently granted MC chip submits 7DTD/PZ, accidentally granting 7DTD. Keep stored and effective grants distinct and use the server's canonical response after role changes.

### F26 P2 Concurrent Crew changes disagree with persisted permissions

`src/components/crew-list.tsx:59` sends whole-list PUTs while world chips remain enabled. Clicking MC then PZ can issue `[minecraft]` followed by `[minecraft,zomboid]`; reversed completion leaves only MC persisted while both chips stay lit and both requests report success. Rejected requests restore captured stale arrays; network rejections have no recovery.

Serialize changes per user, consume canonical saved values, and prevent stale responses from overriding newer intentions. These are security-sensitive permissions, so optimistic color alone must not prove persistence.

### F27 P2 Delayed file reads can save into a different root

`src/components/file-browser.tsx:87` captures the read's root in its request but stores only the filename on completion. `:118` saves using the currently selected root. Start reading PZ Config's `yoshling.ini`, switch to All before completion, then save the late-opened editor: it writes `/zomboid/yoshling.ini` rather than `/zomboid/Server/yoshling.ini` and reports success.

Track endpoint, root and path together as the file identity; cancel or reject obsolete reads/listings. This is distinct from the fixed failed-read buffer corruption.

### F28 P2 Read only users still receive controls that always refuse

**Existing unfinished capability UX.** Console Send, backup Create/Restore/Delete, PZ mod Add/Edit/Remove, map Save and update Check remain offered without capability checks. Files tabs are offered even though their GET requires `settings.read`; the shared sidebar advertises ADMIN-only Whitelist to non-admins.

Relevant anchors are `game-console.tsx:157`, `game-backups.tsx:291`, `zomboid-mods.tsx:153`, `zomboid-maps.tsx:318`, `zomboid-update-status.tsx:166`, and `game-sidebar.tsx:58`. The corresponding write APIs generally refuse correctly. Extend the existing `can` contract to these controls and explain read restrictions. This finding is UX, not an authorization bypass.

### F29 P2 PZ initial errors become a permanent loader or render exception

`zomboid-quick-settings.tsx:134` returns its skeleton for `values === null` before rendering the warning set after a failed GET. Initial failure therefore leaves an indefinite loader.

`zomboid-maps.tsx:62` assigns an error JSON body as state without checking HTTP status or shape, then `:111` calls `state.maps.map`. A denied/failed read can reach the page error boundary. Separate loading, loaded and failed states; offer retry and retain usable prior content only with a freshness indicator.

### F30 P2 The monitor calls stale values live indefinitely

`src/components/server-monitor.tsx:46` keeps the last successful result after failed polls and provides neither last-success time nor error state. `:115` continues to display “Live” and animate the dot even if the server has stopped since that reading. `src/lib/use-games.ts:261` similarly retains snapshots silently.

Show data age and failed polling separately from the last known run state. Keep historical readings available, but do not describe them as current measurements.

### F31 P2 The memory drift repair button is disabled

`memory-card.tsx:178` tells the operator to save again when configured and container values differ. The chosen value starts from the configured value, so `dirty` is false and the Save button at `:215` is disabled. The advertised repair requires choosing a different heap first.

Allow applying the existing desired value when the verified container differs, with normal operation admission. This also needs to distinguish an unreadable/missing live value from a verified match: `getMemoryState` currently treats `liveGb === null` as applied.

## Background work and transport

### F32 P2 The documented watcher switch does not override Compose

`docker-compose.yml:333` explicitly sets `PZ_UPDATE_WATCH:"true"`, overriding the `.env` loaded at `:310`. Both poll intervals are also literals. `src/instrumentation.ts:84` reads the resulting process environment.

Setting `PZ_UPDATE_WATCH=false` in `.env` and recreating web therefore cannot disable automatic restarts as the operational docs promise. Interpolate these operator settings from `.env`, then verify the recreated container's effective values. This is source-confirmed; the watcher was not disabled during the audit.

### F33 P2 Telnet rejection or partial output is accepted as success

**Existing timeout defect with a reproduced authentication variant.** `src/lib/telnet.ts:55` resolves on timeout and `:112` resolves on close; status at `:175` accepts nearly any nonempty reply. `sdtdSaveWorld` at `:204` ignores the returned response.

An isolated loopback fake server sent a password prompt followed by a denial and closed. The actual module returned reachable with 0/8 players, and save returned normally despite no authenticated command executing. Recognize authentication/command completion, reject incomplete sessions, and verify save results. This compounds F13 and makes the next real 7DTD startup an essential control verification.

### F34 P2 Update lookup failure is described as up to date

**Existing and recorded in the 7DTD deep doc.** `src/app/api/7dtd/update/route.ts:33` does not map configured `stable` to Steam's `public` branch, and failure at `:72` becomes `updateAvailable:false`. The UI cannot distinguish a healthy comparison from a failed lookup.

Use explicit checked, unknown and update-available results, and resolve branch aliases. Production currently uses `latest_experimental`, so the alias defect is conditional; the unknown-result defect applies to any upstream failure.

## Existing feature limits and other open risks

- Pack imports still discard version pins and create duplicate saved sets. Applying a pack while also changing the server's Minecraft version is wanted but unbuilt. These are already on the central open list.
- Import represents a saved dependency list, not a complete `.mrpack` installation. Pack overrides, configuration, datapacks and other non-jar content need an explicit completeness contract; selecting all mod jars alone does not establish that a published pack was reproduced.
- Routine MC backups are world-only. PZ/7DTD backups of running games are not atomic filesystem snapshots; refusing a scheduled backup when players are present only judges the initial probe and does not prevent someone joining mid-copy. Archive integrity hashes establish byte identity, not gameplay consistency.
- All file DELETE routes accept a path resolving to their root. The September audit already recorded this. A mount's eventual `EBUSY` should not be treated as proof that recursive child deletion is harmless; destructive root removal should require a dedicated explicit action.
- The sign-in whitelist does not revoke existing JWT sessions. The JWT callback re-reads role/grants but not whitelist membership; if a DB user disappears, it also leaves previous claims intact. There is no normal user-delete route, so that latter case is an administrative recovery/deletion concern.
- Role changes and app whitelist writes still lack durable Activity records; source inspection of their handlers confirms this part of the earlier audit remains. Console commands also need deliberate audit coverage.
- Upload HMAC validation falls back to a predictable development secret when `AUTH_SECRET` is absent (`upload-token.ts:19`). Production is configured; new deployments should refuse the token path without a real secret.
- Migrations remain manual, there is no Prisma generation hook for a fresh install, and the authenticated local UI recipe is still absent. These are known handoff/development gaps, not newly broken runtime features.
- The stats collector still has no timeout or overlap guard, and writes its history non-atomically (`src/instrumentation.ts:24`). The operations doc's statement that all three timers have re-entry guards was wrong; only the watcher and backup timer do.
- Upstream HTML is rendered through `html-react-parser` or raw Markdown HTML in the mod details dialog. Sanitization and executable-content behavior require a focused check; this audit does not claim a proven XSS.
- PZ's scanner honors saved map order in current source (`pz/search_folder.sh:113`). The historical closure text saying no reorder can survive restart is contradicted by that implementation. A fresh order round trip was not performed live. Existing map directories are not recopied on normal mod updates, but the game can overlay Workshop map files; stale map behavior needs resolved-file evidence before filing it as a defect.

## Regression coverage and frontend assessment

The tests exercise many of the difficult invariants: stopped-world preservation, no-op power behavior, RCON timeouts/framing, archive integrity, parsers, settings round trips, mod provenance, and operation conclusions. The September audit's fixed injection, root-prefix, binary-editor, compose-clobber, stale-IP and stopped-history bugs were not counted as current defects.

All seven React hook lint errors were inspected. None established an infinite render loop: the affected effects depend on mount/stable state or externally changing values, and the modpacks declaration-order error concerns a hoisted function invoked later. The lint failures still obstruct a useful gate; fix or narrowly justify them instead of describing all errors as harmless `any` warnings.

The current tests did not catch F01, F04, F07–F13, F17–F21 or the concrete frontend failure paths above. Future regression tests should cover route authorization, symlink admission, reset retention across world names, container memory limits, failed-apply retries, failed initial loads, HTTP gateway responses, and out-of-order writes. Follow the project's mutation rule when adding them: break the protected behavior and prove the test fails. No new tests were added in this audit.

The observed desktop layout is coherent, with consistent world identity, clear hierarchy, an honest installed-jar reconciliation surface and native controls exposed in the sampled accessibility trees. PZ Backups also rendered in Firefox's phone viewport. The main frontend problems are failed reads, stale state, role capability coverage and mutation feedback. Mobile overflow across all pages, keyboard traversal, contrast, both themes, and all destructive confirmation flows were not comprehensively exercised; source review alone cannot certify them.

## Repair order

1. Close file/ZIP physical-boundary escapes, remove secrets from images, and patch affected runtime dependencies.
2. Protect reset recovery copies and world admission; align memory limits; make settings and credential restores retryable and verifiable.
3. Serialize writes and complete Minecraft dependency/import/rollback contracts.
4. Repair ambiguous timeout feedback, failed-load protection, Crew/file identity races and role controls.
5. Finish the already-requested pack version/pinning work, developer setup, remaining audit records and broader UI verification.

Real game joins and controlled restore/startup exercises remain necessary before claiming end-to-end correctness for Minecraft or 7DTD. PZ's daily use is real evidence of its current world running, not proof of every management operation.
