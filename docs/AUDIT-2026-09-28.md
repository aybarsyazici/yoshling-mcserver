## 1. Verdict in five lines

1. **The newer core is genuinely good and you should not spend time there**: the heartbeat control lock, `containerRunning`/`unreachable`/`looksStuck` (the "no-recovery bug" your docs still call unfixed — it's fixed), `restartGame` as staged stop+start, `cachedProbe`, `compose.ts`'s scoped `patchServiceEnv`, `setMemory`'s create-not-up ordering with read-back, and `gameGate` on all 88 handlers. Session + per-world gating is complete and has no fall-through.
2. **The damage is concentrated in the pre-generalisation Minecraft layer** — `/api/server/backups` (root command injection, `rm -rf world` before verifying the archive), `/api/mods/install-modpack` (still rewrites `docker-compose.yml` from a 2-service template, inside `catch {}`, armed by 3 of your 6 saved modpacks), `/api/server/properties` (no locked keys at all; can permanently blind the app to MC).
3. **The repeated pattern is "reports success after doing nothing or the wrong thing"**, not crashes: 2 of 6 7DTD Quick settings write XML properties that don't exist; PZ's entire map-order card is overwritten by the image's own `sed` on every boot; a modpack apply that installs 0 of 166 mods toasts green; every backup restore returns `{success:true}` without ever stopping the server.
4. **Two worlds are running right now** (7DTD 2d, PZ 3h, 2.2 GB swap) — but *not* from a code path. Three verifiers traced it to a hand-run `docker start` during the 2026-09-26 netcup recovery. The real defect is that nothing detects or refuses co-residency and no container has a `mem_limit`. The six findings blaming `restartGame`/`withGameStopped` are wrong about the mechanism.
5. **Minecraft has never started on netcup, and its first start will probably fail**: DB says 26.1.2, compose and the container say 1.21.4, and `/data` holds a 26.1.2 Fabric launcher plus three 26.1.2-dependent jars. With `restart: unless-stopped` that's a crash loop the probe renders as perpetual "starting".

## 3. By area

**Lifecycle.** Sound where it was rewritten recently, unenforced at the edges. The heartbeat lock (expiry on `beat`, not `since`), `setControlStage`, `OperationBanner` and `restartGame` as explicit stop+start are all correct and the comments explaining them hold up. The one thing to know: **`powerOn` is the only path that evicts other worlds**, and four others start containers without it — but the live two-world state was *not* caused by any of them, so fix the guard, don't rewrite `withGameStopped` (it cannot start a stopped world). `containerState()` failing open is cosmetic hardening, not the live defect three dimensions claimed.

**Backups.** The weakest area, and the one you asked about. Creation works and the 7DTD/PZ bundles are genuinely self-contained (verified on disk). Everything after creation is soft: no restore stops the server, all three report success on failure, MC deletes before verifying, and there is no retention, no pruning, no disk check, no scheduling, no checksum, and no download path. **The single most important fact: MC's newest backup is 2026-05-30, 7DTD has one from 2026-07-23 (predating both the migration and the config wipe), and PZ — played daily with 89 mods — has one from 2026-09-18.** A manual-only button reliably produces exactly this. Listing also gunzips every archive (5.0 s / 7.3 s measured), and a listing timeout renders as "No backups yet."

**Memory.** The best-engineered feature here and the one whose docs are most wrong. There is no `MAX_GAME_GB`; the cap is `/proc/meminfo − HOST_RESERVE_GB(2.5)` = **13 GB**, and the whole chain verifies end-to-end (compose `12288m` → container env → live `-Xmx12288m`). `create --force-recreate` correctly keeps a stopped world stopped (`yoshling-mc` sits in `created`, never started). Real gaps are peripheral: the 1 GB/`MIN_MEMORY` floor, ADMIN-only vs MOD-everything-else, no `setControlStage` on a multi-minute operation, fractional GB passing validation, and `liveEnv` swallowing a failed `inspect` into the reassuring "applied" state.

**MC mods and modpacks.** A "modpack" is a saved list of Modrinth project refs plus a target version/loader — **nothing ever downloads or extracts a `.mrpack`**, so there's no zip-slip surface, but `overrides` (configs, KubeJS, datapacks) are silently dropped, which for a config-heavy pack like COBBLEVERSE means the jars install and the game is still wrong. There is **no way to install a single mod**: `/api/mods/install` has had zero callers in every revision, `checkForUpdates`/`updateMod` are fully written and unreachable, `ModRequest` + `mods.request` exist with no route or UI, and the Technic browser is dead code the copy still points users at. Nothing reconciles the DB against the mods folder (`readdir` is imported into `mod-manager.ts` and never called), so a profile switch leaves untracked jars loading beside the new set while the Installed tab insists they aren't there.

**Project Zomboid.** The `.ini` layer is the best code in the repo — line-based, comment-preserving, correct for `;` and `=` in values — and the `.acf` brace-bounded parsing plus `installedModIds` reading declared ids from `mod.info` are solid. The `INFRA_KEYS` guard is *not* a security boundary and shouldn't be treated as one (four bypasses, including the file browser). The single most important thing: **every `.ini` write is an unlocked non-atomic read-modify-write** across six entry points, so two overlapping saves lose one silently — and the map card it feeds can't affect the game at all.

**7 Days to Die.** `/api/7dtd/update` does exactly what CLAUDE.md claims — `patchServiceEnv` on `START_MODE`, `recreateService`, a `finally` that restores `START_MODE=1`, then `assertSingleContainer`. No hand-built `docker run` anywhere. The rest is thinner: the update *check* reports "up to date" whenever the Steam lookup fails (and `branchInfo` will never resolve `stable`, since the Steam key is `public`), the world uploader's content-root finder is wrong for two realistic layouts and its save branch flattens into `Saves/` unloadably, and **7DTD has no mod management despite running three mods in `Mods/` today**. Telnet always sends `exit` (correct), but the immediate `socket.destroy()` still produces the `IOException` spam the comment says it prevents, and a hard timeout *resolves* with a partial buffer — so a wedged server reads as "online, 0 players."

**Auth.** Structurally the cleanest dimension: all 88 handlers resolve a session, every game-scoped handler has a world gate, all 22 `denyGame` and 22 `gameGate` sites early-return correctly, and role escalation is genuinely closed (`users.manage` ADMIN-only on both routes, self-demotion blocked, `games` CSV whitelist-parsed, `hasPermission` fails closed). The gaps are one layer in — **capability**, not session — plus one class the per-route table structurally cannot see: "the gate is right and the handler is injectable" (#1). Note that **every finding phrased "a read-only MEMBER can…" is latent**: prod is 5 ADMIN + 1 MOD scoped to `zomboid`. Also: removing someone from the whitelist does not end their session (30-day JWT; only `role`/`games` are re-read).

**Files and console.** Path traversal is genuinely blocked — `..`, absolute paths, encoded separators and a bogus `root` all fail, `.env` and `docker-compose.yml` are unreachable from any root, and there are no symlinks in any volume today. Containment is nonetheless a separator-less string prefix with no `realpath`, so `/sevendtd` grants `/sevendtd-config`. The editable-extension allowlist is client-only; console commands are **not audited at all** while file edits are; and both features bypass `PERMISSIONS` with inline role string comparisons, making file delete a second undocumented ADMIN-only capability.

**Status and stats.** Probes and boot progress are the best UX in the app (three distinct states for stopped/starting/wedged, per-boot percentages, one `awk` pass). The data behind the graphs is not trustworthy: zeros for stopped containers, an unreachable offline branch, **30 minutes of total history** (360 points at 5 s) with no rollup, a memory metric measured against *host* RAM rather than the game's heap (so an 11.5/12 GB PZ shows ~74% and looks fine), and a collector with two bare `catch {}`, no timeout and no overlap guard. `stats-history.json` is an orphan; `/api/server/{stats,status,control}` are dead routes.

**Parity.** The abstraction is real and adding a fourth game would mostly work. Exactly one asymmetry is deliberate and correct (7DTD has no heap setting — Unity native, no memory env on the container at all) — **and even that one is mis-implemented**, because `MemoryCard` isn't mounted on the 7DTD page, so the explanation never renders. Everything else that differs differs by accident of build order.

## 6. What we still don't know

Straight from the completeness critic.

**Routes and features nobody opened.** 7 of 54 route files were never read by any dimension. Six are harmless read proxies. The seventh cluster is `/api/server/{properties,ops,mc-whitelist}` — three live cards on `/minecraft/settings`, zero mentions across ten dimensions. Parity's matrix *names* the gap ("no locked keys") and files no finding. That's #3 above, and it is the only critical-shaped thing the audit found by accident. Also: **no `error.tsx` exists anywhere** (`find src/app -name error.tsx` → 0), so mc-mods' `exportData?.modpack.name` TypeError doesn't "take out the Mods page" — it white-screens the whole app with no recovery.

**Is `docker-compose.yml` app-owned or git-owned?** Nobody asked, and it sits underneath ~8 findings. Memory presents "prod compose is byte-identical to git HEAD" as reassurance; mc-mods presents the same fact as proof that **every memory and version change the UI makes is silently reverted by the next deploy** (citing f0cf692, "Commit the 12 GB PZ heap so a deploy stops reverting it", as prior art); parity assumes someone reconciles by hand. Until you decide, every fix that writes compose is unresolved — and the 26.1.2-vs-1.21.4 split is either evidence of this or evidence of a swallowed recreate failure, and nobody could tell which.

**Severity calibration is not load-bearing.** 9 of 13 criticals were downgraded by their own verifier. `install-modpack` was upheld **critical** by two verifiers and downgraded to **high** by two others, for the substantive reason above — there is no agreed severity for the audit's most-reported finding. Conversely the one finding that survived every verifier at critical (MC backup injection) was found by a *minority* of dimensions and rated **high** by a third, and authz — whose entire assignment was a 54-route table — declared `/api/server/*` "clean" and never saw it. A per-route gate table structurally cannot detect "the gate is correct and the handler is injectable." **Duplicate count is not evidence of severity here**: the most-duplicated finding (one-world, 6 filings) was downgraded by every verifier that examined its causal claim.

**Four medium findings rest on an unmeasured number.** "Cloudflare's 100 s origin timeout makes a successful restart toast 'Network error'" appears in four dimensions. Nobody timed an operation, nobody checked the zone's actual timeout (plan-dependent and configurable), nobody checked Caddy's own timeouts — and two verifiers proved `:3000` is directly internet-reachable, so the premise that traffic goes through Cloudflare is itself only partly true. Unreconciled.

**Risk classes nobody looked at.**
- **The audit trail is not trustworthy and no finding says so.** 20 of 37 mutating routes write no `Activity` row: both console routes, all three backup routes, `install-modpack`, `/api/settings`, `/api/7dtd/{reset,update}`, every modpack route, `/api/whitelist`, `/api/users/[id]/role`, `/api/server/{ops,properties,mc-whitelist}`. Four verifiers had to work *around* exactly these holes to do the 2026-09-26 forensics. Three filed narrow versions; none stated the systemic one: **who may sign in, who is ADMIN, who is a Minecraft operator, and every destructive restore can all be changed with no record.** (Backups also claims "eighteen other API routes record to db.activity"; the real number is 11 files.)
- **No `Activity` retention.** Unbounded growth in the same SQLite file as everything else.
- **The database layer was never audited.** Single-file SQLite, zero transactions anywhere, and `auth.ts`'s `jwt` callback hits it on *every* request with a fail-open `if (dbUser)` and no `else`. Nobody asked what happens while it's locked — e.g. while a backup `tar` copies `/app/data`, which is where `yoshling.db` lives.
- **No container sets `mem_limit`.** A clause inside two findings, never filed, and it's the only thing that would contain the over-commit everyone found.
- **No dimension exercised the app.** No writes on prod, nothing started or stopped, no browser session. Every "reports success" and every UX finding is read from source. The two most destructive paths have **never been run in production** — no `presreset-*` archive exists and there is no Activity row for any restore — so their failure modes are entirely theoretical.
- **There is no test suite** (`find` for `*.test.*`/vitest/jest/playwright → nothing). ~190 findings will be fixed and verified by hand against a live server people play on daily. No dimension mentioned this; it is the multiplier on every item in §7.

**Still open after 10 audits + 10 verifications.** Who started 7DTD at ~13:31 and ~13:56 UTC on 2026-09-26 (three verifiers converged on a non-interactive `ssh host 'cmd'` — `.bash_history` unchanged since Sep 14 — none could prove it). **The two-world state is still live and no finding says who should fix it.** Whether `install-modpack`'s destructive branch has ever fired (compose is intact; "never fired" and "a deploy repaired it" are indistinguishable). Whether `26.1.2` is a version `itzg` can boot at all. Whether SteamCMD prints `Success. Downloaded item` for an already-current item — if not, `seedMods`' `ok < len` check throws on a *successful* run and, given the missing `finally`, takes PZ down for nothing. Whether 7DTD and MC survive Docker's default 10 s stop (both `StopTimeout=<nil>`; PZ got 300 s only after a save was SIGKILLed).

## 7. Suggested order of work

Grouped by what shares a deploy or a restart. **Everything in groups B and D is a single `docker compose build web && up -d --no-deps web` — no game restart, no player impact.**

**A — Right now, no deploy, no code (minutes).**
1. Close the ports: add DROP rules to `DOCKER-USER` for 3000/8080/8081 (takes effect immediately, no container touched). The compose-level fix (`127.0.0.1:3000:3000`, `127.0.0.1:8081:8081`, drop 8080) needs a web + 7dtd recreate — defer it to group C. *Needs no restart.*
2. Decide the two-world state. Stopping one world is **player-visible**; do it deliberately, and note that nothing will tell you if it recurs until group B lands.
3. Take a manual backup of all three games. PZ has 10 days unprotected and it's played daily. This is also your only net for group B, given no tests.
